MODULE 01 · THE LANGUAGE MODEL

What exactly is a Large Language Model?

A Large Language Model (LLM) is a machine-learning model trained on very large collections of language data. During training it learns statistical and structural relationships between tokens: which expressions tend to occur together, how grammar works, how concepts are expressed, and how context changes the likely continuation of a sequence.

▤

Large

“Large” commonly refers to the scale of the training data, model parameters and computational resources. It does not mean the model contains a perfect copy of the internet or knows every fact.

SCALE
Aa

Language

The model is designed to work with language-like sequences. Depending on the system, it may also process code, images, audio or other modalities.

SEQUENCES & CONTEXT
◉

Model

A model is a learned mathematical function. Its parameters encode patterns acquired during training and are used to calculate likely outputs for new inputs.

LEARNED PARAMETERS

LLM is not the same as a search engine or database

LLM GENERATION

Produces a likely continuation

An LLM uses the prompt and available context to generate tokens. Unless connected to retrieval or tools, it is not necessarily looking up a verified record for each statement.

Example: Ask “Explain photosynthesis simply” and it generates an explanation from patterns learned during training and the supplied context.

SEARCH / DATABASE LOOKUP

Finds stored information

A search engine retrieves indexed pages; a database query retrieves records matching defined conditions. These systems can provide direct source records, although those records still need quality checks.

Example: Query a student database for a specific student ID and retrieve the matching row.

✦

Precise mental model: an LLM is a trained model that generates a sequence based on learned patterns and current context. It can be connected to search, databases and tools, but generation and retrieval are distinct operations.

MODULE 02 · HOW THE MODEL IS BUILT

How does an LLM learn language patterns?

At a high level, training repeatedly shows the model token sequences and asks it to predict a missing or upcoming token. The prediction is compared with the training target. An optimisation process calculates how the parameters should change to reduce the prediction error. This is repeated across huge numbers of examples.

01Text corpusBooks, articles, code and other permitted data
→
02TokenisationConvert text into token IDs
→
03Model predictionEstimate the next-token distribution

Understand the training loop

  1. Prepare a corpus: collect and process permitted text and other training examples. Data curation matters because duplication, low-quality content, bias and missing coverage affect what the model learns.
  2. Tokenise: split the sequence into tokens and map them to numeric IDs that the model can process.
  3. Predict: provide a sequence prefix and ask the model to estimate the next token.
  4. Calculate loss: compare the predicted probability distribution with the actual target token. A loss function quantifies how far the prediction is from the target.
  5. Update parameters: backpropagation calculates gradients; an optimiser uses them to update model parameters.
  6. Repeat and evaluate: train over many batches, then evaluate on held-out data to check how well the model generalises.

What are parameters?

Parameters are numerical values inside the model that are adjusted during training. They are not a simple list of facts or manually written rules. Together, they determine how input representations are transformed into output probabilities. More parameters can increase capacity, but parameter count alone does not guarantee accuracy, reasoning quality or safety.

✦

Important distinction: training changes model parameters. Inference normally uses the trained parameters to generate an answer; it does not automatically update the model after every conversation.

MODULE 03 · THE GENERATION ENGINE

Next-token prediction: how a response is built.

At inference time, the model receives a prompt as tokens. It calculates a probability distribution over possible next tokens. A decoding strategy selects one token, appends it to the sequence, and runs the process again. Repeating this loop creates a complete response.

Autocomplete analogy: when your phone suggests the next word in a message, it is estimating plausible continuations from context. An LLM performs a far more capable version of sequence prediction, repeatedly, across a much larger learned representation.

Does the model always choose the highest-probability token? Not necessarily. A decoding method may sample from a probability distribution, or use a more deterministic strategy. Temperature and top-p can affect the candidate distribution and selection. That is why repeated runs can differ.

MODULE 04 · THE ARCHITECTURE

Transformers and attention: using relationships in context.

A Transformer is a neural-network architecture used by many modern language models. Its key contribution is an attention mechanism that allows token representations to incorporate information from other relevant tokens in the sequence. The architecture also uses feed-forward layers, residual connections, normalisation and positional information.

INPUT TOKENS“The animal did not cross the road because it was tired.”

Attention in plain language

Consider: “The animal did not cross the road because it was tired.” To interpret “it”, the model can use information from “animal” and “tired”. Change the sentence to “The animal did not cross the road because it was flooded.” Now “it” is more likely to refer to the road. Attention provides a mechanism for relating tokens rather than treating every token in isolation.

MODULE 05 · TEXT REPRESENTATION

Tokens and tokenisation: the units a model processes.

A language model does not directly process a sentence as a human-readable string. A tokenizer converts text into smaller units called tokens, then maps those tokens to numeric IDs. A token may be a whole word, part of a word, punctuation, whitespace-associated text or another unit depending on the tokenizer.

ORIGINAL TEXTGenerative AI is changing software development.
↓ TOKENIZER
Generative AI is changing software development.

Illustrative split only. Different tokenizers can produce different boundaries and token counts.

Why not simply split by spaces?

Space splitting would treat “playing”, “played” and “player” as unrelated whole units. Subword tokenisation can reuse pieces across words, helping represent rare or unfamiliar terms without needing a unique vocabulary entry for every possible word.

Punctuation, numbers, code and multilingual text can be segmented in tokenizer-specific ways.

Why token counts matter

Input instructions, conversation history, documents and generated output all consume tokens. Token limits affect how much information can fit in a request, while token volume can influence latency and usage cost on hosted services.

A word is not guaranteed to equal one token. The “four characters per token” rule is only a rough English estimate.

MODULE 06 · WORKING MEMORY FOR A REQUEST

Context windows: what can the model consider right now?

A context window is the maximum amount of tokenised information a model can process as context for a particular request, subject to the model and product's limits. It may include system instructions, developer instructions, conversation history, the current prompt and supplied documents. Generated output also consumes the available context budget in many systems.

THE MODEL'S AVAILABLE CONTEXTLIMITED CAPACITY
InstructionsRules and task requirements
ConversationRelevant previous messages
Current promptThe question being asked now
Documents / dataContent supplied for analysis
Context budget
Finite

The desk analogy

Imagine a desk with limited space. You can place instructions, notes, a question and reference documents on it. A larger desk allows more material, but it does not guarantee that every page is relevant or that the reader will interpret every detail correctly. Context selection remains important.

What happens when the context is too long?

  • The application may reject the request, truncate content, summarise older messages or manage context using another strategy.
  • Important early instructions may no longer be available if they are outside the effective context.
  • Large context can increase processing time and cost, depending on the service.
  • Relevant details can be buried inside irrelevant material, making the task harder even when they technically fit.

Better practice: prioritise the source material, remove duplication, label important constraints and ask the model to identify missing information instead of guessing.

MODULE 07 · CONTROLLING GENERATION

Temperature, top-p and max tokens: three different controls.

Generation settings influence how a model selects tokens and how much it is allowed to produce. They are not knowledge controls: increasing temperature does not make a model smarter, and increasing max tokens does not make it more accurate.

°

Temperature

Changes the sharpness of the probability distribution used for sampling. Lower values generally make selection more concentrated around high-probability options; higher values generally allow more variation.

◉

Top-p

Nucleus sampling limits candidate tokens to the smallest high-probability set whose cumulative probability reaches a chosen threshold, then samples within that set.

↕

Max output tokens

Sets an upper bound on generated token count. It controls the allowed response length, not an exact word count or guaranteed completeness.

!

Task fit

Settings should be tested for the task and model. Platform defaults, supported ranges and interactions differ, so avoid treating one configuration as universally best.

MODULE 08 · WHAT LLMs ARE USEFUL FOR

What can LLMs actually do?

LLMs are flexible interfaces for language tasks. Their value grows when the task, instructions and source material are clear, and when outputs are checked against the real requirements.

✎

Generation

Create a first draft of an email, explanation, product description, test case or outline. The output is new text, so it should be reviewed for accuracy, tone and policy.

CREATE
▤

Summarisation

Condense long reports, meeting notes or feedback into key points. Check that exceptions, dates, numbers and qualifications have not been dropped.

CONDENSE
⌕

Extraction

Identify named entities, invoice fields, dates, owners, deadlines or action items from unstructured text. Validate missing and malformed fields.

STRUCTURE

Reasoning assistance

LLMs can help break a task into steps, compare alternatives, explain concepts and surface assumptions. However, an answer that looks logically structured may still contain an invalid step or unsupported conclusion.

Good use: ask it to explain a proposed solution, list assumptions and test edge cases.

Code assistance

They can explain unfamiliar code, draft functions, suggest refactoring, create test ideas and interpret error messages. They can also invent APIs, omit edge cases or generate insecure code.

Good use: compile and run generated code, review dependencies and test expected plus unexpected inputs.

MODULE 09 · LIMITATIONS & TRUST

Why can an LLM be confident and still be wrong?

Language generation optimises for producing plausible continuations under the model's training and instructions. Plausibility is not the same as evidence. A responsible user understands common failure modes and builds verification into the workflow.

RISK 01

Hallucinations

The model may generate plausible but unsupported or false information: fabricated citations, incorrect figures, invented APIs or inaccurate explanations.

Response: verify factual claims against authoritative sources, supplied documents, executable tests or actual system records.

RISK 02

Knowledge freshness

Training knowledge may not include recent events or current product details. A model without live retrieval may not know what changed yesterday.

Response: use current trusted sources or approved connected tools for time-sensitive information.

RISK 03

Non-determinism

The same prompt can produce different outputs because of sampling, context, model versions or service behaviour.

Response: use clear schemas, controlled settings where available, automated validation and repeatable test cases.

RISK 04

Context limitations

Relevant information may be missing, truncated, poorly prioritised or misunderstood within a long request.

Response: provide focused context, cite source sections and ask the model to state what information is missing.

RISK 05

Bias and uneven performance

Training data and evaluation coverage can produce unequal error rates across languages, groups or situations.

Response: test representative cases, monitor outcomes and involve appropriate human review.

RISK 06

Privacy and security

Prompts may contain confidential information. Outputs may expose sensitive details or follow malicious instructions embedded in untrusted content.

Response: follow organisational data policies, minimise sensitive input and treat external content as untrusted.

◎
HUMAN REVIEW

Keep a person accountable for high-impact decisions

Healthcare, lending, hiring, legal and safety-related decisions need appropriate domain expertise, evidence, oversight and appeal mechanisms. A fluent response is not a substitute for professional judgement.

MODULE 10 · CHOOSING A MODEL

How should a team choose an LLM?

Do not select a model only because it is popular or has the largest parameter count. Select it by testing whether it meets the task's quality, operational, security and governance requirements.

Evaluation lensQuestions to askExample evidence
Task fitCan it reliably summarise, extract, reason or write code for this use case?Representative task benchmark
QualityAre answers accurate, complete, grounded and consistent?Human review and automated tests
ContextCan it handle the required prompt and source material?Context limit and long-document tests
OperationsAre latency, throughput, cost and availability acceptable?Load tests and usage estimates
GovernanceDoes it meet privacy, security, compliance and deployment rules?Security review and vendor terms

Run a fair model comparison

  1. Collect representative examples, including normal cases, difficult cases and edge cases.
  2. Define a scoring rubric before testing: correctness, completeness, format compliance, groundedness and safety.
  3. Run the same tasks with each candidate model and comparable instructions.
  4. Record quality, latency, cost and failure patterns; do not rely on one impressive demonstration.
  5. Choose the simplest model that meets the requirements, then monitor it in production.
✦

There is no universal best model. The best choice is the model and system configuration that meets your actual task requirements with acceptable risk and operational cost.

MODULE 11 · PUT IT INTO PRACTICE

A reliable LLM workflow: context → generation → verification.

A strong workflow makes the model's job clear and creates a deliberate check before the output is used. The model should not be asked to fill gaps with guesses.

02Supply contextProvide relevant source material and constraints

→
04VerifyCheck facts, calculations and omissions
→
05Use responsiblyApprove, revise or reject the result
SAMPLE TASK

Summarise customer feedback without losing meaning

Weak instruction: “Summarise these comments.”

Stronger instruction: “Summarise the supplied customer comments for a product manager. Identify the three most frequent themes, include one short representative quotation per theme, separate observed facts from interpretation, mention contradictory feedback, and do not invent counts. If the source does not support a conclusion, say so.”

Verification: sample the original comments behind each theme, check quotations exactly, confirm any counts and look for minority views that the summary may have hidden.
